# Проверка качества поиска

Команда `regagent evaluate` сравнивает BM25, BGE-M3 dense и hybrid RRF
на одном наборе вопросов и одном зафиксированном корпусе.

## Первый набор

`data/evaluation/drafts/legal_acts_ru_kk.yaml` содержит 60 черновых вопросов:
30 русско-казахских пар по загруженной версии закона «О правовых актах».
Вопросы и предварительные ссылки на статьи подготовлены AI и ещё не проверены
экспертом. Это пилотный набор для разработки, а не независимый тест диссертации.

Все вопросы имеют `review_status: draft`. Без явного `--allow-draft` запуск
останавливается. Результаты такого запуска помечаются `pilot_unreviewed`.

## Запуск

Из корня репозитория, с запущенным PostgreSQL и построенным индексом:

```powershell
poetry run regagent evaluate data/evaluation/drafts/legal_acts_ru_kk.yaml `
  --pipeline-signature 8cc110d69566d224ebebde20f022187eb19cead5992ced909fcb088ed697a88d `
  --chunking-strategy legal_structure `
  --allow-draft `
  --output-dir artifacts/my-pilot-run
```

Каталог результата должен быть новым, чтобы не перезаписать предыдущий эксперимент.
`--strategies bm25` позволяет выполнить проверку без загрузки embedding-модели.
По умолчанию запускаются все три метода. `--k 1 3 5 10` задаёт срезы метрик.

При наличии BGE-M3 в кэше можно полностью отключить обращения к Hugging Face:

```powershell
$env:HF_HUB_OFFLINE = "1"
$env:TRANSFORMERS_OFFLINE = "1"
```

## Что сохраняется

- `dataset.yaml`: точная копия входного набора вопросов.
- `manifest.json`: SHA-256 набора и корпуса, ревизия модели, настройки поиска,
  версии библиотек, Git commit, признак изменённого дерева, хеш исходного кода.
- `resolved_cases.json`: вопросы, фильтры конкретных версий и локальные ID релевантных чанков.
- `results.json`: метрики и найденные фрагменты для каждого вопроса и метода.
- `summary.csv`: средние метрики отдельно для `ru`, `kk` и всего набора;
  UTF-8 с BOM подходит для открытия в Excel.
- `review.md`: вопросы и полные тексты размеченных фрагментов со ссылками на источник
  и хешами версии — материал для проверки разметки человеком.

Все результаты находятся в игнорируемом Git каталоге `artifacts/`.

## Значение метрик

Единица ранжирования — **чанк**. На пилотном этапе размечена статья: каждый чанк,
содержащий исходный раздел этой статьи, считается релевантным. Учитываются все
исходные разделы чанка, включая фрагменты fixed-window, пересекающие границы статей.
Простое текстовое упоминание номера статьи не делает чанк релевантным.

- Recall@k: доля всех релевантных чанков, найденных в первых k результатах.
- MRR@max(k): среднее значение `1 / позиция первого релевантного чанка`;
  ноль, если среди возвращённых результатов релевантного чанка нет.
- nDCG@k: дисконтированный выигрыш с бинарной релевантностью, нормированный
  на идеальное ранжирование. Релевантный чанк на позиции r даёт `1 / log2(r + 1)`.

Средние считаются по вопросам. Переводные пары связаны общим `pair_id` и не являются
60 независимыми наблюдениями. Общая таблица содержит 30 связанных пар вопросов.

Разметка по статье приблизительна: отдельный фрагмент длинной статьи может не
содержать ответ на конкретный вопрос. Поэтому эти числа проверяют работоспособность
эксперимента; они не оценивают точность юридического ответа, генерацию LLM или
преимущество метода на независимых данных. При сравнении стратегий чанкинга меняется
число релевантных чанков — прямое сравнение их Recall требует более точной разметки
по доказательным фрагментам или отдельной метрики на уровне статей.

## Воспроизводимость

Источники задаются языком, официальным URL и SHA-256 нормализованного текста.
Вопросы ссылаются на источник и номер статьи, а не на случайные UUID базы.
При запуске эти ссылки преобразуются в ID чанков текущей базы. Поисковый фильтр
ограничивается выбранными версиями; другие редакции не попадают в результаты.
Хеш корпуса учитывает текст, порядок, происхождение и конфигурацию чанков,
но не зависит от локальных UUID.

Запуск останавливается при отсутствующей редакции, неразрешённой статье,
повторяющихся case_id, неполном dense-индексе или изменении корпуса во время оценки.
Равные оценки ранжируются по данным источника/тексту вместо случайных ID.
Это не обещание побитовой идентичности GPU-вычислений на разном оборудовании.
Проверка даты действия закона здесь не выполняется: оценивается зафиксированный
текст источника, а не актуальность правовой нормы на сегодняшний день.

## Проверка и следующий эксперимент

1. Проверить каждый вопрос, казахскую формулировку и релевантные статьи в `review.md`.
   Особенно проверить исключённые статьи, сноски и нормы с отложенным вступлением в силу.
2. Исправить YAML. Для проверенных случаев указать `review_status: reviewed`,
   `reviewer` и `reviewed_at` (дата ISO). Не менять статус массово без проверки.
3. После проверки сохранить набор в `data/evaluation/reviewed/` и запустить без
   `--allow-draft`. В отчёте останется точный хеш проверенного набора.
4. Расширить корпус несколькими тематически близкими законами, добавить сложные
   вопросы с несколькими источниками и отдельные проверки отсутствующего ответа.
5. До настройки reranker сформировать независимый тест. Разделять данные по
   документам/темам и `pair_id`, чтобы переводы одного вопроса не оказались
   одновременно в обучении и тесте. Добавить второго разметчика и согласование спорных случаев.
